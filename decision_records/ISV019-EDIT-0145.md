## Applicator development and transaction boundary

The frozen applicator is 105,516 bytes / SHA-256
`071EDD8556A0C654421D660D652AE69B89ECA656B130273F1149FF4B1A66072A`.
Two deterministic default dry runs and two self-tests were byte-identical and
made no workspace changes. The self-test covers five transformation guards and
49 hostile transaction families comprising 65 effective transaction subcases.

Earlier candidates remain adverse evidence rather than being erased:

- `3C8CCADB…` lost stage custody before `os.replace`, mishandling both
  pre-mutation failure and completed-then-raised replacement;
- `81B812…` could orphan low-level exclusive-create artifacts after `fstat`,
  final-`lstat`, or cleanup uncertainty;
- `27A602E0…` overstated pathname-race protection, destroyed rollback evidence
  before final target probes, and could leak probe descriptors;
- `FA0FEFB4…` still allowed a raw closer that raised before closing to leak the
  descriptor.

The accepted design records create attempts before `open`, binds descriptor and
path identity immediately, creates all rollback images before stages, never
discards ownership history, reconciles replacement on return and exception,
preserves recovery on uncertainty, audits the coherent four-target vector before
destroying rollback evidence, removes the lock last, and never rolls back a
committed vector because cleanup failed. Descriptor closure is total and tested
for before-close, completed-then-raised, and no-op behavior.

The O_EXCL lock coordinates cooperating invocations only. Portable Python cannot
make a pathname `replace` or `unlink` conditional on a previously observed inode;
an actor that ignores or replaces the lock can race that final syscall. Observed
pre/post states are reconciled, but there is no uncooperative-writer
serialization, cross-crash atomicity, or four-file filesystem-atomicity claim.

The first frozen metadata-sealer candidate, 80,746 bytes / SHA-256
`EF939553E754DF306FDF389BE208AFE55F2F8BF6714C625856FF366F889E789E`,
was independently rejected and invalidated before application. Its final audit
checked the source-applicator residue namespace but not both metadata token
namespaces. A simulated committed seal cleanup failure could therefore leave
five seal artifacts while a later worklog append ignored them and still reported
zero residue. The replacement audits every seal and worklog lock, stage, and
rollback pathname—including the deliberately unused absent-sidecar rollback
name—before planning, before the pending verifier and append, during guarded
validation, before recovery destruction, before lock removal, and again after
cleanup. Only exact artifacts owned by the current in-flight invocation may be
temporarily present. A dedicated regression proves that committed seal residue
blocks the worklog append before that append creates any artifact.

The next metadata-sealer candidate, 93,839 bytes / SHA-256
`6E8EA02E174B15CCE34F19B407FD20017093CFFD3CA58C9BA213C62005B3A6AE`,
was also independently rejected and invalidated before application. It passed
the new residue regression, but passed an invocation-owned `FileIdentity`
dataclass from one dynamic applicator-module instance into an audit using a
separately loaded instance. Python dataclass equality is class-sensitive, so
identical device, inode, and file-type values compared unequal and the real
in-flight validation would reject its own exact seal or worklog artifacts. The
replacement crosses module boundaries only with primitive
`(device, inode, file_type)` tuples. Separate end-to-end temporary transactions
now exercise both the seal and worklog validation paths with distinct module
classes, followed by zero-residue post-cleanup audits.
